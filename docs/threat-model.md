# 威胁模型

系统要防住服务器侧泄露和网络窃听；对「服务器下发恶意前端代码」只能缓解；对用户电脑中木马无能为力。

完成标准：数据库被完整拖走时，攻击者在不知道主密码（和 Secret Key）的情况下拿不到任何明文，包括网址和标题。

| 场景 | 处理 | 靠什么 |
|---|---|---|
| D1 数据库或备份被拖走 | 防住 | 只存密文；主密码经 Argon2id 慢哈希；认证哈希和加密密钥分离 |
| 网络中间人 | 防住 | 全站 HTTPS + HSTS；传输的本来就是密文 |
| 在线暴力破解登录 | 防住 | 登录限流、可选 TOTP 二次验证、Cloudflare Access 先拦一层 |
| 已登录设备丢失（已锁定） | 防住 | 密钥只在内存，锁定即丢弃；本地缓存只有密文 |
| 服务器擅自换朋友公钥 | 防住 | 共享前核验公钥指纹，核验结果存在自己的加密保管库里 |
| 服务器篡改或互换密文 | 防住 | AEAD + AAD 绑定条目 ID 和保管库 ID |
| Cloudflare / GitHub 账号被盗，推送恶意 JS | 缓解 | 硬件密钥二次验证、分支保护、严格 CSP、无第三方脚本；v2 浏览器插件可根治 |
| 主密码太弱 + 数据库泄露 | 防住 | Secret Key 参与派生，拖库后无法离线爆破；Argon2id 和注册强度检查（zxcvbn ≥ 3）兜底 |
| 用户电脑中木马、键盘记录 | 不防 | 任何密码管理器都防不住 |
| 用户在钓鱼域名输入主密码 | 不防 | 靠用户警惕；建议只用书签或主屏幕图标打开 |
| 忘记主密码且无恢复码 | 不可恢复 | 零知识架构的代价，注册时强制保存应急卡 |

## 已知残余风险

以下几条由 P6 独立审查指出，**目前不防**（H1/M1/M2 的根治需要修改 crypto-spec，待确认）：

- **服务器可以伪造或替换保管库密钥（P6 H1）**：能写数据库的人可以插入一个假的「个人保管库」或替换 `sealed_vault_key`，诱导客户端把新数据写进他能解开的库。目前的缓解：解不开的库和条目不再静默丢弃，界面会显示红色警告；出现多个个人库也会警告。
- **登录时服务器返回的公钥没有与私钥核对（P6 M1）**：服务器可以把你的公钥换成攻击者的，影响之后新建的共享库。
- **恢复码等于完整访问权（P6 M2）**：恢复码和 Secret Key 印在同一张应急卡上，拿到卡就能接管账号，不需要主密码。应急卡要像现金一样保管。
- **回滚与隐藏（P6 L1）**：条目的 AAD 不含版本号，服务器可以把条目回滚到旧版本、隐藏或复活已删除的条目，客户端无法发现。

- 已加入共享库的成员（含 viewer）在密码学上持有 vaultKey，可以抄走库内全部内容；移人后必须轮换密钥，并去对应网站改密码。
- 服务器能看到：邮箱、公钥、每个库的条目数量与大致大小（256 字节粒度）、修改时间、成员关系、登录 IP 的哈希。
- 页面内注入的脚本可以调用 IndexedDB 里不可导出的 Secret Key CryptoKey 做派生；挡住 XSS 的是 CSP + Trusted Types。
- 剪贴板自动清空只是尽力而为：剪贴板管理器、系统历史可能已经保存。
